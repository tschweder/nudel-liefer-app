# Driver offline copy (NUD-081)

What is stored on the driver's phone, where, for whom and for how long.

| Data                                                                                                        | Where                                       | Key                                 | Written by                                                 | Removed                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ----------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Today's tour JSON (stops, items, texts in all locales, notes, signed photo URLs, revision / change markers) | IndexedDB `nudel-driver-offline` / `tours`  | user id (one record)                | page (`syncDriverTour`) after `GET /api/driver/tour/today` | next sync of another user; any record of another day; when nothing is released; logout / login page                                                                             |
| Photos of that tour                                                                                         | Cache Storage `nudel-driver-photos-v1`      | `/api/driver/photo-cache/<photoId>` | page (downloads the signed URL with CORS `GET`)            | photos no longer in the tour; logout / login page                                                                                                                               |
| Queued stop taps (outbox, NUD-082)                                                                          | IndexedDB `nudel-driver-offline` / `outbox` | `clientMutationId`                  | page (`enqueueMutation`)                                   | when the server has answered (applied, replayed or rejected); an undo of a not yet sent tap removes it; entries of another driver 3 days after their tap. NOT on logout         |
| Queued photos (NUD-083)                                                                                     | IndexedDB `nudel-driver-offline` / `photos` | `clientMutationId`                  | page (`enqueuePhoto`)                                      | when the server has registered or finally rejected the photo; replaced by a newer photo of the same slot; entries of another driver 3 days after they were taken. NOT on logout |
| Notices (a tap the server did not apply)                                                                    | IndexedDB `notices`                         | `clientMutationId`                  | page / service worker after the answer                     | when the driver taps "Verstanden"; other drivers' after 3 days                                                                                                                  |
| App shell, offline shell pages `/<locale>/driver/offline-shell`                                             | service worker precache                     | build revision                      | service worker install                                     | next worker version                                                                                                                                                             |

- The service worker never stores authenticated HTML, RSC payloads or API answers. It only (a) serves the public, personal-data-free shell page when a load of `/<locale>/driver` or `/<locale>/driver/stops/<id>` fails, and (b) answers `/api/driver/photo-cache/<id>` from the photo cache.
- The shell page reads IndexedDB and renders the same components as the server pages from the same model (`src/lib/driver-tour-model.ts`).
- Requirements: the R2 bucket's CORS rule must allow `GET` from the app origin (docs/env.md), otherwise photos are not cached and the app shows "offline partly ready" instead of "ready offline".

## Start URL of the installed app (NUD-106)

- All manifests (`/<locale>/manifest.webmanifest`, one per locale only for the localized `name`) use the same locale-neutral `start_url` `/driver?source=pwa`, `id` `/driver` and `scope` `/`. `proxy.ts` redirects every path without a locale prefix (so also this one, 307, `Cache-Control: no-store`) to the driver's CURRENT language: session locale (updated by the language switcher) -> `NEXT_LOCALE` cookie -> Accept-Language -> `de` (`src/lib/locale-redirect.ts`). Not logged in: the redirect leads to the driver login in the cookie / Accept-Language language.
- Offline: the worker treats `/driver` like any driver navigation (network only, nothing stored). When it fails, the generic `offline.html` is answered under the URL `/driver`; its script (`public/offline.js`, precached with it; no inline script because of the CSP, NUD-110) reads the `NEXT_LOCALE` cookie (written by the login and the language switcher; German if missing or unknown) and replaces the location with `/<locale>/driver`, which the worker answers with the offline shell of that language.
- An app installed before NUD-106 keeps its old `/<locale>/driver` start URL until the browser refreshes the manifest (Chrome on Android does this by itself within a day or so; if not, reinstall). iOS before 16.4 ignores the manifest and starts on the page that was open when "Add to Home Screen" was used; reinstall there too. Not testable in the sandbox (NUD-105).

## Map view offline (NUD-108)

- Default: **no tiles are stored.** Tile providers' terms generally forbid bulk pre-fetching / offline copies (the OSM tile usage policy explicitly), so the app does not cache a bounding box.
- The driver's map view (and the admin tour map) degrades gracefully instead: when the browser is offline, or four tile requests in a row fail while "online" (provider down, dead Wi-Fi), `TourMap` removes the tile layer (no request storm, no grey broken-tile grid), draws a plain neutral background with a faint grid and shows a notice above the map ("Kartenhintergrund offline nicht verfügbar" / "离线时无法显示地图背景", `maps.*` messages, WiFi-off and map-pin-off icons, `role="status"`). Numbered stop markers, depot marker and the route line (from the stored tour, also in the offline shell) stay, the map can still be zoomed and panned, marker tooltips (customer name) still work. The tile layer returns by itself when the connection is back.
- Opt-in `MAP_TILE_CACHE=1` (default OFF, see `docs/env.md` for the provider-terms caveat): the worker caches only tiles the page requested (browser-cache-like), CORS responses with status 200 only, LRU 300 tiles, 7 days (`src/sw/tile-cache.ts`, cache `nudel-map-tiles-v1`, cache-first). Tiles contain no personal data. A tile that is not in the cache still falls back to the plain map above, and zoom levels / areas the driver never viewed are of course missing.
- Not testable in the sandbox: real tile provider with CORS, storage quota on phones.

## Mutation queue (NUD-082)

- A tap on Delivered / Problem / Undo is first written to the IndexedDB outbox (`clientMutationId` = UUID, type, stop, reason / note, `createdAt` = time of the tap), then the screen changes at once (optimistic overlay on the page data: `src/lib/offline/outbox.ts`, `use-overlay.ts`). Online it is sent immediately, offline when the connection is back.
- Triggers (`OfflineSync`): app start, the `online` event, the app becoming visible again (these three skip the backoff), every 60 s and after every new tap (these respect it). Never gated on `navigator.onLine`. Backoff after failed attempts: 2 s, 4 s, 8 s ... capped at 5 min, reset by a success. Background Sync (`sync` tag `nudel-outbox`, Chromium only) lets the service worker send the queue of the driver that owns the stored tour copy when the app is closed; other browsers rely on the page triggers.
- `POST /api/driver/sync` (DRIVER only, JSON, strict zod, 1..50 entries, <= 256 KiB): entries are applied in tap order, each through `applyStopMutation` (idempotent by `clientMutationId`, advisory lock per tour date). Answer: per entry `applied | replayed | rejected(error) | retry` and the authoritative stop states of the touched tours. Longer queues are sent in chunks of 50.
- Time: `completedAt` and the 5-minute undo window use the time of the tap (`createdAt` clamped to [server now - 24 h, server now]).
- Conflict rule: the office changing a stop (a re-release that changed or added it sets `Stop.adminChangedAt`) after the tap makes the server reject the tap (`changed_by_office`); a removed stop, an inactive tour or an already closed stop are rejected too. The state of the server wins, the driver sees a notice per rejected tap until he acknowledges it.
- Undo: a queued completion that is not on its way is removed from the queue (no delivered + undo pair); otherwise an undo is queued behind it.
- Customer key (NUD-142, D27): a driver sets or corrects the key number of the customer at a stop with an entry of `type: "key"` (`hasKey`, optional `keyNumber`, max 20 characters) in the same queue and the same endpoint. The server applies it through `applyDriverKey` (`customer-key.ts`): the stop must belong to a tour of the acting driver (any tour state, otherwise `not_found`), idempotent by `clientMutationId` (recorded in `StopMutation`, kind `KEY`), no conflict rule and no approval: the driver's field knowledge wins. The change and its audit entry `customer.key` (before / after) share one transaction. The answer repeats `hasKey` / `keyNumber` per stop, which patches the stored tour copy; the screen shows a queued key at once (`overlayStop`). A key entry is not a completion: it never takes part in the undo / double-tap rules of the stop taps.
- Logout does not delete unsent taps (they belong to that driver and are sent after his next login); the login pages still purge the tour copy and the photos.

## Photos taken by the driver (NUD-083)

- The stop screen offers "Foto aufnehmen" in the empty photo placeholder and "Foto ersetzen" below a present photo (`<input type="file" accept="image/*" capture="environment">`). The picture is decoded, scaled to 1600 px, re-encoded as JPEG (EXIF / GPS dropped) in the browser, shown as a preview, and only queued when the driver taps "Foto verwenden".
- Queue: IndexedDB `nudel-driver-offline` (DB version 3) / `photos`, key `clientMutationId`. A row holds the resized blob, stop, customer, kind, size, time, and (after the upload succeeded) the `storageKey`. Removed when the server has registered or finally rejected it; a newer photo of the same customer and kind replaces an unsent older one; photos of another driver are dropped 3 days after they were taken. Like unsent taps they survive logout.
- Sending (`photo-outbox-flush.ts`, page and Background Sync in the worker, same triggers and backoff as the tap outbox: start, `online`, visible, 60 s, new photo; 2 s doubling to 5 min), oldest first, per photo:
  1. `POST /api/uploads` -> presigned PUT URL (valid 5 min, so grant and PUT happen in one attempt) and `PUT` of the blob to the bucket (CORS must allow `PUT`, docs/env.md). Afterwards the row is saved with the `storageKey`: a retry never uploads again.
  2. `POST /api/driver/photos` `{ clientMutationId, stopId, kind, storageKey, width, height }` (DRIVER only). The customer is derived from the stop; the stop must belong to the driver's own tour (RELEASED / IN_PROGRESS / COMPLETED) of today or yesterday (factory time zone). `Photo.clientMutationId` is unique: a retry whose answer was lost returns the same photo (`replayed`), also when two retries run at once. The photo becomes the current one, the previous current photo stays as history (`isCurrent=false`); the admin customer page shows "Aktualisiert von Fahrer X am <date>".
  3. On success the blob is put into the photo cache under the real photo id and the stored tour copy is patched, then the row is removed and the pages refresh.
- Final rejections (`not_found`, `tour_not_active`, `invalid`, `key_in_use`, `mutation_conflict`, or three times `object_missing`) remove the photo and leave a notice card ("Das Foto wurde nicht übernommen"); network errors, 5xx and 401 / 403 keep it queued.
- On screen the newest queued photo is shown from the local blob (object URL, works offline) with the badge "Wartet auf Versand"; after the server took it "Gesendet" is shown for 20 s on top of the not yet refreshed page data. The top-bar badge counts queued taps and photos together.
- Storage cost: one JPEG of roughly 150 - 500 KB per queued photo (normally gone within seconds of having a connection).

## Error pages when offline (NUD-094)

The driver error page (`src/components/driver/driver-error.tsx`) checks `navigator.onLine`. Offline it shows a calm "no connection" page instead of "something went wrong"; its button reloads the page so the service worker serves the cached shell, and it reloads by itself when the connection returns. The error pages inside `driver/(app)` keep the shell mounted, so queued taps keep syncing. Sentry events are not queued offline; they are dropped (see `deploy.md` section 12).
