# Driver offline copy (NUD-081)

What is stored on the driver's phone, where, for whom and for how long.

| Data                                                                                                        | Where                                       | Key                                 | Written by                                                 | Removed                                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ----------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Today's tour JSON (stops, items, texts in all locales, notes, signed photo URLs, revision / change markers) | IndexedDB `nudel-driver-offline` / `tours`  | user id (one record)                | page (`syncDriverTour`) after `GET /api/driver/tour/today` | next sync of another user; any record of another day; when nothing is released; logout / login page                                                                     |
| Photos of that tour                                                                                         | Cache Storage `nudel-driver-photos-v1`      | `/api/driver/photo-cache/<photoId>` | page (downloads the signed URL with CORS `GET`)            | photos no longer in the tour; logout / login page                                                                                                                       |
| Queued stop taps (outbox, NUD-082)                                                                          | IndexedDB `nudel-driver-offline` / `outbox` | `clientMutationId`                  | page (`enqueueMutation`)                                   | when the server has answered (applied, replayed or rejected); an undo of a not yet sent tap removes it; entries of another driver 3 days after their tap. NOT on logout |
| Notices (a tap the server did not apply)                                                                    | IndexedDB `notices`                         | `clientMutationId`                  | page / service worker after the answer                     | when the driver taps "Verstanden"; other drivers' after 3 days                                                                                                          |
| App shell, offline shell pages `/<locale>/driver/offline-shell`                                             | service worker precache                     | build revision                      | service worker install                                     | next worker version                                                                                                                                                     |

- The service worker never stores authenticated HTML, RSC payloads or API answers. It only (a) serves the public, personal-data-free shell page when a load of `/<locale>/driver` or `/<locale>/driver/stops/<id>` fails, and (b) answers `/api/driver/photo-cache/<id>` from the photo cache.
- The shell page reads IndexedDB and renders the same components as the server pages from the same model (`src/lib/driver-tour-model.ts`).
- Requirements: the R2 bucket's CORS rule must allow `GET` from the app origin (docs/env.md), otherwise photos are not cached and the app shows "offline partly ready" instead of "ready offline".

## Mutation queue (NUD-082)

- A tap on Delivered / Problem / Undo is first written to the IndexedDB outbox (`clientMutationId` = UUID, type, stop, reason / note, `createdAt` = time of the tap), then the screen changes at once (optimistic overlay on the page data: `src/lib/offline/outbox.ts`, `use-overlay.ts`). Online it is sent immediately, offline when the connection is back.
- Triggers (`OfflineSync`): app start, the `online` event, the app becoming visible again (these three skip the backoff), every 60 s and after every new tap (these respect it). Never gated on `navigator.onLine`. Backoff after failed attempts: 2 s, 4 s, 8 s ... capped at 5 min, reset by a success. Background Sync (`sync` tag `nudel-outbox`, Chromium only) lets the service worker send the queue of the driver that owns the stored tour copy when the app is closed; other browsers rely on the page triggers.
- `POST /api/driver/sync` (DRIVER only, JSON, strict zod, 1..50 entries, <= 256 KiB): entries are applied in tap order, each through `applyStopMutation` (idempotent by `clientMutationId`, advisory lock per tour date). Answer: per entry `applied | replayed | rejected(error) | retry` and the authoritative stop states of the touched tours. Longer queues are sent in chunks of 50.
- Time: `completedAt` and the 5-minute undo window use the time of the tap (`createdAt` clamped to [server now - 24 h, server now]).
- Conflict rule: the office changing a stop (a re-release that changed or added it sets `Stop.adminChangedAt`) after the tap makes the server reject the tap (`changed_by_office`); a removed stop, an inactive tour or an already closed stop are rejected too. The state of the server wins, the driver sees a notice per rejected tap until he acknowledges it.
- Undo: a queued completion that is not on its way is removed from the queue (no delivered + undo pair); otherwise an undo is queued behind it.
- Logout does not delete unsent taps (they belong to that driver and are sent after his next login); the login pages still purge the tour copy and the photos.
